# Sonnet 5.5 as the main agent: Ghostty settings window

## What to take from it

- **Use Sonnet as a main seat for backend or safety work with tests.** The config engine it wrote itself was sound, and it held under an independent adversarial gate.
- **Do not let Sonnet own a taste call or a done-claim on a UI.** It approved a page that drifted from the mock after a 40-second look, and it accepted a sub-agent's report as proof.
- **It follows the gcc's procedure closely and its judgment loosely.** Every skill in the chain ran in order. Most misses were places where the procedure was satisfied in letter and the owner's intent was not.
- **Its sub-agent briefs were the best part.** Reuse their shape.

## Where it left expected behavior

Expected behavior here means what the owner's request and standing rules plainly called for.

1. **It asked a settled question three more times.** The variant question was asked at 14:18, 14:23 and 14:26. After "go with defaults" at 14:45, it still wrote "the variant question is unanswered" at 14:47.
2. **It handed off work its own plan kept in-house.** The plan's model routing kept engine, schema and mocks with the main agent and named no builder for the front end. Then the whole front end went to one Sonnet builder in a single 27-minute pass.
3. **It promised a diff review and never did it.** At 16:11 it wrote "Reviewing the full diff is the next step after the gate". No file under `app/public/js` was ever opened by the main agent.
4. **It said the page matched the mock when it did not.** "The rendered pixels match the confirmed composition" came about 40 seconds after the builder finished, from two of the builder's screenshots. The real page differs from the mock in help text, group strip, row order, the cursor-blink control and the blue "previews live" tags.
5. **It stamped the parity ledger in bulk.** One `sed` set all 15 rows to PASS. Two rows were already false, because the fix round had removed a server route and changed the file writer.
6. **It led with "built, validated and fixed".** It never looked at the page after the fix round, and the saved screenshots predate it. It did list that gap, but below the headline.
7. **Its replies were too long and sent twice.** Owner-facing replies ran 2,500 to 3,000 characters of bold-label bullets, and five went out twice after a format gate re-emit.

## Where its judgment was thin

Judgment-aware means weighing what matters to this owner, not only what can be checked.

1. **The mock showed content the build could not produce.** The mock had about 12 hand-picked settings with hand-written help. The build shows all 211, with help cut from Ghostty's docs ("A theme to use."). The owner approved a look on content that never existed, and nothing in the plan or brief named the gap.
2. **It turned taste notes into checkable rules and stopped there.** "No needless borders", "tooltips with shortcuts" and "one solid button" became grep checks. "Usable and ergonomic", the owner's actual goal, got no acceptance row, so nothing could fail on it.
3. **It spent its care where it was easy to prove.** The engine already passed 44 of 44 tests. Most of the red-then-green work, the mutations and the race probes went there again. The UI the owner judges by eye got two screenshot glances.
4. **It read reports as proof.** The builder marked rows PASS while their own evidence said "not exercised" or UNCONFIRMED, and the main agent accepted them. The memory rule "a sub-agent's done is data" was in context.
5. **It skipped re-checking the riskiest change.** The fix round rewrote how list keys are written into the owner's config, after the independent gate had run. Only the author's tests stood behind it.
6. **It picked the reviewer for defects, not confusion.** The validator ran `/ui-categorical-check`, which finds contrast and clipping problems. `/ui-gripe`, the skill for "why is this hard to use", was never called, though "usable and ergonomic" was the brief.

What it did well against the gcc:

- It ran `/plan` with a current-behaviour statement, then `/build-ui`, a Codex plan review with a model smoke test, `/mock-app` variants, two decision pages and `/bloop` with an independent gate.
- Every brief carried the five dispatch clauses, sandbox rules, the owner's verbatim words and explicit acceptance rows.
- It filed proposals for real friction and wrote a clean checkpoint.

## Use it for, avoid it for

| Use Sonnet 5.5 for | Avoid it for |
|---|---|
| A main seat on backend, data or safety work with a test suite | A main seat that owns a UI's look or its done-claim |
| Writing sub-agent briefs and validator attack lists | Judging whether a page reads well |
| Running a long skill chain in order | Judging when a procedure has been met but the intent has not |

If Sonnet runs a UI build again, add these rows to the brief:

- The mock is drawn from the real schema and real help strings.
- One acceptance row is about reading the page: "a first-time reader finds and understands font size, theme and padding in under 10 s", judged by `/ui-gripe` on the final render.
- The main agent compares the final render with the approved mock in both themes before any done-claim.
- Any fix round that touches the file writer goes back through the gate.
