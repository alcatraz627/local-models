## 2. What was attempted

- **The tool itself is solid engineering.** `bin/imagine` has a real iteration model (`redo`/`vary`/`refine` from a history index), style presets, `--enhance` (local LLM prompt-rewrite), img2img (`--from`/`--strength`), and a well-reasoned preflight that refuses to run on a half-downloaded model cache. That preflight was born from a real 38-minute silent-hang incident on 07-13.
- **The convergence-loop design** (`docs/10-visual-compare-design.md` section 11) is the most ambitious piece. `imagine` proposes, `see diff` measures ($0, about 1s), a judge classifies divergences, `vis-ledger.py` tracks fixed/persisting/new, `imagine refine` applies a seed-locked correction, and the loop repeats. This is a genuinely good idea for driving a generated image toward a target look without burning judge calls every round.
- **It was exercised exactly once**, as a documented experiment (`.claude/output/20260713-imagine-loop/round-trip.md`), 2 rounds, about 3 min/round on qwen, against a fictional "beanu-boss-spaceship" reference. It worked. 3 of 5 divergences were fixed in one seed-locked pass, and it surfaced a real, useful finding: pixel/region scores saturate on composition change and are a poor convergence signal for imagegen specifically; the judge's transition classification is the real signal. That finding was folded back into docs/10. But the loop has never run again since, on anything real.
- **The design role never had a real caller.** No product surface (Versable's `walmart-mvp`, `staging-enhancement-product`, `landing-app`, `internal-dashboard`, etc.) sources an image from `imagine`. Every one of the 1,986 image files in `~/Code/Versable` and the 174 SVGs there were produced some other way: design-tool exports, screenshots, hand-authored SVG. `/svg` (vector icons/logos/diagrams) has a real, separate identity in this account and is explicitly the routed alternative for icon/logo/vector work.

## 3. Gaps: why zero runs in 48 days

Four converging reasons, weighted by evidence.

1. **No workflow ever pulled it in.** Every one of the 18 runs was an ad hoc, standalone "let me try this" call, never a step inside a doc-writing, deck-building, or product-asset skill. `/deck`, `/word-doc`, `/create-report`, `/readme` (which explicitly wants "a pixel-art cover image") could all plausibly call `imagine`, and none do based on this repo's own logs; whether those skills route elsewhere is unverified, noted in section 9.
2. **Latency is a real tax with no payoff attached.** Qwen runs cost 2 to 4 minutes each (180-248s observed). That is tolerable for a one-off "let me see a cat" but hostile to any iterative design workflow, and the one lane built to amortize that cost, the convergence loop, itself needs 2+ rounds times 3 minutes to converge: 6 to 10 minutes of wall time per asset, unattended-capable but not something anyone reached for twice.
3. **The owner's stated preference works against this lane directly.** Project memory `user_images_ephemeral_parse_now` says: never pitch screenshot-recall systems, invest in read-quality instead. That is a preference for reading images over generating and storing them. Raster image generation for its own sake is the opposite motion: it produces a new asset to be stored and later reasoned about, not a read of something that already exists.
4. **Vector already owns the product-asset lane this account actually has demand for.** Every real asset need found in `~/Code/Versable` is icons, logos, diagrams, or screenshots, which is the `/svg` skill's territory. That skill composes Claude's own SVG authoring (no backend, $0, instant, exact edits) rather than a 3 to 8 minute diffusion render. Raster gen's actual differentiators (photorealism, painterly concept art, texture) never appeared as a real need anywhere in this account's product work.

## 4. Ideal workflow, if the lane earns a job

If this account develops a real need for raster assets (a landing-page hero, a marketing/deck cover photo, a concept-art mood board), the ideal shape already exists in the design docs and just needs a caller:

```
prompt/idea --> imagine --enhance "..."  (local LLM prompt-rewrite for thin ideas)
                    |
                    v
            candidate.png ($0, 2-4 min, qwen)
                    |
              +-----+-----+
              v           v
      see (native vision)   /vis-compare (if there's a reference to match)
      "does this look right?"     see diff -> judge -> ledger -> imagine refine (loop)
              |
              v
      accept / imagine vary (new seed) / imagine refine (steer, same seed)
```

The missing piece is not more imagegen tooling. It is a caller: a doc/deck/readme skill step that says "if a cover image is wanted, offer `/generate-image`" and actually exercises the offer, plus (for product icon sets specifically) `lib/asset-verify.py`'s already-built rung-quality gate, which has never been run against a real generated icon set either (only a validation-harness exercise, `.claude/output/20260713-asset-verify-validation/`).

## 5. Bridge or retire: recommendation

**Retire schnell now. Keep qwen and the tool as a thin, occasionally-used capability. Do not invest further build effort in the convergence loop until a real caller exists.**

Evidence:
- schnell is unambiguously dead weight. It is 31 GB, had 9 uses all before the 08-10 review explicitly said to drop it, has zero uses in the 48 days since, and `config.sh` already documents the decision not to use it; only the `trash` command was never run. Action: `trash ~/.cache/huggingface/hub/models--black-forest-labs--FLUX.1-schnell` reclaims 31 GB for zero loss. This repo's own CLAUDE.md "no idle penalty" hard rule applies as much to disk as to warm processes.
- Qwen-Image (49 GB) and the ControlNet-Canny model (3.3 GB) are lower-confidence keeps. Qwen is the one model that actually got used for anything resembling real work (the mascot series, a UI-mockup prompt), and 49 GB is not urgent to reclaim on a 64 GB unified-memory machine with no stated storage pressure. But it has also been silent for 48 days. If this were re-audited in another 4 to 6 weeks with continued zero usage, dropping it too and re-pulling on demand (the preflight already handles a clean cold start) becomes the right call. This report does not recommend that yet; it recommends watching it, since one real use (the mascot chain) is a thinner signal than zero but not nothing.
- The convergence loop (docs/10 section 11) is well designed and already proved itself once. It should not be deleted or treated as failed. But it should also not receive further engineering investment (more judge policy, more ledger features) until something outside this repo actually calls `imagine` twice in a design iteration. It is validated infrastructure waiting on demand, not demand waiting on infrastructure.
- The `generate-image` gcc skill is honest and well built: it states the latency up front, refuses silent downloads, and offers the real iteration verbs. Keep it as is; it costs nothing idle and is the correct thin wrapper already.

**Net effect of the one recommended action:** reclaim 31 GB, change nothing about capability (qwen was already the default), and bring `config.sh`'s own documented decision into agreement with the disk.

## 6. State of local image generation on Apple Silicon, Aug 2026

Two independent, dated external sources, plus this repo's own June 2026 internal survey (`.claude/output/20260619-open-model-landscape/image-video-gen.md`), which is itself still largely current since diffusion-model turnover is slower than LLM turnover.

- **mflux** (filipstrand, the MLX-native runtime `imagine` already uses) supports, as of 2026: FLUX.1 (dev/schnell), FLUX.2 (Klein 4B, Apache-licensed; Klein 9B, non-commercial; dev 32B, non-commercial), Qwen-Image (20B, Apache 2.0, best open text-in-image), Z-Image-Turbo (6B, Apache, about 8 steps, the fastest quality/speed tradeoff on MLX), plus smaller entrants (ERNIE-Image, FIBO, Ideogram-4-in-mflux with license unverified for the last one).
- **Speed on Apple Silicon, measured:** FLUX.2 Klein 4B renders 1024x1024 in 30 to 40 seconds on an M1 Max with mflux ([lilting.ch, 2026](https://lilting.ch/en/articles/flux2-klein-4b-mflux-iris-m1-max)). Separately, community benchmarking reports FLUX-dev-4bit generation on M5 is 3.8x faster than M4 ([explainx.ai, Aug 2026](https://explainx.ai/blog/dflash-2-mlx-m5-max-local-inference-august-2026)). Combined, a Klein-4B-class model on this machine's M5 Pro plausibly lands well under 15 seconds per image, a different world from the 2 to 4 minute qwen-20B runs actually logged. The model this repo defaults to (qwen, 20B, non-distilled) is the slow end of the current landscape; a distilled Apache model (Z-Image-Turbo 6B or FLUX.2 Klein 4B) would cut latency roughly 10 to 20x while staying commercial-license-clean.
- **Editing/ControlNet:** Qwen-Image-Edit and FLUX.2 Klein both do instruction-based image editing. This repo already has FLUX.1-dev-ControlNet-Canny cached (3.3 GB, unused) for edge-guided generation.
- **Text rendering:** Qwen-Image remains the open leader for in-image typography, the one differentiator that matters if this lane ever targets infographics, posters, or UI mockups with legible text. One of the 18 historical prompts was exactly this: a SaaS UI mockup with card text.

## 8. Tooling for product assets specifically

This is the more relevant finding for this owner's actual work, per the repo evidence in sections 2-4.

- **OG/social cards and doc covers:** the standard 2026 approach is Satori (`@vercel/og`), HTML+CSS to SVG/PNG, no headless browser, works at the edge, purpose-built for exactly the "cover image for a report/doc" need `/readme` already states it wants ([vercel.com/docs/og-image-generation](https://vercel.com/docs/og-image-generation)). Playwright screenshot of a styled HTML page is the batch/CI-time fallback when Satori's template limits bite, about 2s/image, fine for build time, not per-request ([dev.to/morinaga, 2026](https://dev.to/morinaga/what-i-learned-generating-og-images-for-articles-with-playwright-and-zero-api-cost-3c0e)).
- **Icon sets:** the `/svg` skill (Claude authors markup directly, no diffusion backend) plus this repo's own `lib/asset-verify.py` (already built: verifies every derived size rung of an icon against a best-achievable resample, not the diffusion model) is the correct pipeline shape for icon work. It has just never been exercised against real generated output.
- **What a small software company actually uses, per current market coverage:** SVG-first, component-driven asset generation (Figma exports, hand-authored icon sets, Satori-rendered social cards) dominates for product UI. Diffusion image generation shows up for marketing hero images, blog covers, and concept art, exactly the category this account has generated zero of for any real surface.
